# Service API and workflow operation

Updated: **2026-10-09**. Audit results are in the [production code review](../../research/production-code-review-2026-10-09.md) and [verification record](../../research/production-review-verification-2026-10-09.json).

The reference API is implemented with FastAPI over the configured authority store. It has no default bearer token, tenant or repository grant. `create_app()` without an explicit store and token-to-`Principal` configuration returns `503 api_unconfigured` for protected routes. Use loopback for local inspection; external exposure requires a separately reviewed identity/transport and operating configuration. Never place credentials in candidate environments or a repository file.

Construct `service.api.create_app(store, tokens={secret: Principal(tenant_id, subject_id, frozenset(repository_ids), can_review=False)}, artifact_store=artifacts)` in trusted startup code. Tokens must be explicit strings of 24–512 characters; load them from operator-managed secret configuration. Every token identifies one tenant and subject, exact repository grants and allowed profiles. The default profile grant permits production only. A separately granted research profile is still subject to runtime isolation/recovery/capacity gates and declared resources; the grant alone does not demonstrate those gates. The HTTP request body cannot choose a tenant or reviewer.

**VI:** Token được cấu hình ở control plane nối đến identity thật. Client gửi `tenant_id` trong JSON sẽ bị từ chối; không được dùng dữ liệu do caller chọn để cấp quyền. Profile research cũng phải được grant rõ, không tự bật chỉ vì request xin bốn worker.

Supported routes are `POST /tasks`, task status and snapshot, bounded event pages, cancellation, authorized artifact download and authenticated human-review decisions. The API exposes no candidate verification, ownership mutation, budget settlement, sandbox retirement or restore/operator endpoint. Submission body is exactly `{key, contract}`. Cancellation is `{request_id}`; review is `{decision, key}`, with accepted/rejected decisions and the reviewer taken from the principal. Request bodies are bounded before routing, including chunked bodies; duplicate JSON keys, nonfinite values, unknown authority fields and invalid parameters receive structured errors.

For events, `GET /tasks/{task_id}/events` returns a JSON page. Request `Accept: text/event-stream` for a finite SSE page; reconnect with the last consumed event's `Last-Event-ID`. Each row has its own signed cursor so disconnecting halfway does not skip unconsumed events. Do not save a page-end cursor before consuming that page. `410 reset_required` includes an authorized snapshot: discard the old incarnation/gapped cursor and resume from the fresh snapshot cursor. A cursor from another tenant/task is denied. Snapshot/event reads and artifact downloads recheck the principal's current repository grant. Artifact download additionally requires a reference accepted by the domain store; knowing a digest or uploading unbound bytes does not authorize access.

**VI:** Cancel acknowledge chỉ chứng minh quyền tiếp tục đã bị revoke. Sandbox có thể vẫn sống và liability có thể còn giữ. Muốn xác nhận cleanup phải dùng supervisor evidence và `retire_sandbox`; API không cho client tự viết bằng chứng đó.

`service.workflows.LocalOutboxDispatcher` supports a trusted injected synchronous task runner and an explicit `stop_sandbox` cleanup callback. It acknowledges successful dispatches once. Failed calls retain the outbox command. Stale generation/incarnation or terminal start commands are acknowledged as suppressed, while a temporary execution pause retains current queued intent. Known `dispatch`, `candidate_ready`, `verify` and `review_ready` entries are observed as durable-state notifications: acknowledging them never executes a tool, settles a charge or creates verification evidence. The task loop consumes the underlying domain state and receipts. Unsupported kinds and unconfigured cleanup commands remain pending for their owner; the store filters supported kinds before applying its batch limit so they cannot hide later starts. Tests generate over 100 real dispatch notifications, admit a new task, drain bounded pages and verify only the new start runs while the original dispatch effects remain unexecuted/unsettled.

For Temporal, configure an actual SDK `Client`, task queue and `TemporalOutboxRelay`; register `CodingTaskWorkflow` and `TaskActivities.run_step` with the SDK `Worker`. The activity's injected step receives the immutable task identity, generation, bounded step index and a stable idempotency key. It must consult durable domain effect receipts and recheck authority at effect/acceptance boundaries. The wrapper preflight is not an atomic lease and does not guarantee arbitrary injected code is replay-safe. Never put network/filesystem/model effects directly in the workflow body.

The relay binds workflow ID to service incarnation, tenant, task and generation. An ambiguous start is retained for retry. On an already-started response, it describes the existing workflow, **awaits the SDK's asynchronous memo**, and compares command/task identities before acknowledging. The workflow rechecks stop after an awaited activity before returning its result, rolling history or declaring step exhaustion. It executes bounded activities, retries each at most three times, limits history via ContinueAsNew and retains its total step ceiling across histories. It returns explicit orchestration-step exhaustion without inventing a terminal domain outcome. `stop_sandbox` cleanup requires its own trusted dispatcher; signalling a workflow is not physical termination evidence.

The live harness persists complete HTTP response entity bytes before decoding tool/terminal semantics. A received `max_tokens` or invalid tool envelope rejects all tools/completion while valid provider usage still settles once. Missing/untrusted usage, malformed JSON/UTF-8 or transport loss retains conservative unknown billing; raw complete responses remain available for reconciliation. A duplicate tool without its durable known result cannot execute again. Frozen price/bound approval and actual provider reconciliation remain required; these mock-transport regressions do not authorize paid calls.

**VI:** Transport receipt, tool admission và billing không phải một boolean. Một response bị truncate có thể đã tiêu token thật; một result đã có không được biến mất khi settlement đến sau. Stop cũng phải được nhìn lại sau `await`, vì signal có thể đến lúc workflow đang chờ activity.

Historical local evidence on 2026-10-08 included API/storage cases and a real local Temporal run across ContinueAsNew plus both-history replay (SDK 1.34.0, CLI 1.9.1, Server 1.32.0). The 2026-10-09 audit adds actual SDK duplicate-start/memo reconciliation, stop-during-activity before rollover and replay of that stop history. These tests write raw histories in disposable pytest directories. The current verification record supplies exact counts, source hashes and backend versions; older pass totals do not validate later edits.

**VI:** Replay test thật chứng minh code workflow đọc history này mà không lệch quyết định. Nó chưa chứng minh failover của một cluster, tương thích mọi future schema, hoặc engine dài ngày dưới model/API thật. Giữ version và raw history khi đổi workflow để test lại những decision cũ.

Recovery procedure: stop admission separately from execution quarantine; fence previous control-plane actors/environments, activate a new service incarnation and reconcile beyond-backup effects and billing with trusted evidence. Keep uncertain liabilities and occupied sandboxes. Resume only through the store's documented reconciliation transition. Test old cursors/old owner callbacks after restore. No API route bypasses this operator boundary.

Use the [offline schema-1→2 migration](../../service/migrations/002_identity-and-writer-protocol.md) before reopening an old store with current code. Stop all writers, verify a recoverable backup, migrate/test a disposable copy, then upgrade the explicitly authorized store and restart all writers on schema-2 code. Constructor refusal of schema 1 is intentional; no automatic or mixed-version rolling migration exists.

This is local implementation and bounded integration evidence. Identity lifecycle, secret rotation, TLS ingress, SLO traffic, distributed failover, production Temporal persistence/retention, hostile multi-tenant safety and canary operation remain unmeasured until separately configured and exercised.
