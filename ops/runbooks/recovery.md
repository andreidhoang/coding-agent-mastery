# Checkpoint and authority-database recovery

Updated: **2026-10-10**. Current context evidence: [independent review](../../research/context-offloading-independent-review-2026-10-10.md) and [verification](../../research/context-offloading-verification-2026-10-10.json). Prior production audit/evidence: [production code review](../../research/production-code-review-2026-10-09.md) and [verification record](../../research/production-review-verification-2026-10-09.json).

Recovery reconstructs both bytes and their authority. A workspace checkpoint cannot prove an external request did not run, and an authority-database backup cannot prove its old workers stopped. Preserve immutable artifacts, dispatch identities, provider-supported protocol state, receipts, event frontiers and uncertain billing. Stop new admission separately from execution quarantine so normal draining remains possible.

**VI:** Có hai loại khôi phục khác nhau: dựng lại workspace của một task và dựng lại database authority sau mất dữ liệu. Cả hai đều cần biết effect nào chắc chắn đã xảy ra; chỉ copy file hoặc reload snapshot chưa đủ để retry an toàn.

For a task checkpoint/restart:

1. Read the authorized task snapshot and exact checkpoint/artifact references. Verify contract, graph, accepted candidate frontier, workspace digest, message/provider artifacts, next-step marker, unresolved dispatches and resource exposure. Reject changed artifact bytes or stale source evidence.
2. Fence/revoke the old attempt before replacement, and observe local process/environment retirement through its supervisor. An expired lease alone does not free its physical slot. Uncertain teardown remains occupied.
3. Reconcile each unfinished action by stable action/dispatch identity. Reuse a known completed receipt only with its immutable durable result. A terminal effect without that result still cannot be executed again; billing-only settlement preserves existing result evidence. Unknown/in-flight requests cannot be repeated simply because a fresh environment starts. Retain reserved liability until trustworthy effect/usage evidence settles it.
4. Provision a fresh authorized environment, reconstruct only permitted files and retain provider artifacts through their supported adapter. Reacquire current generation/node epoch before accepting new effects, checkpoints or candidates. The harness checks restored contract/workspace digests; the store rechecks owner/dependencies/database deadline at acceptance boundaries.
5. Resume against the same frozen graph and exact candidate identities. Reusing committed patch outputs does not authorize replaying an uncertain tool request. In this reference, a changed graph/requirements requires a new task/contract; do not mutate the existing graph or erase previous events to force a replan.

Inspect [checkpoint storage](../../service/storage.py), [harness restored-state checks](../../service/harness.py), [context projection](../../service/context.py) and [reference engine](../../service/engine.py). The source implements bounded restore checks, provider-artifact retention and saved-output reuse. Local tests exercise a process boundary/reopen and injected crash after integration; they do not demonstrate multi-day live-model continuity or every process-crash window.

Keep complete received provider bodies even when message semantics fail; valid usage may settle independently, while missing/untrusted counters retain exposure. Verifier snapshots and the transport-failure latch prevent mutable inputs or an expected candidate exception from manufacturing success. Container retirement must identify the creation nonce and immutable owned instance ID; a reused name is not cleanup authority. Launcher group retirement is separate from containment and cannot establish that an escaped process or remote effect ended.

**VI:** Reconciliation cần phân biệt “đã nhận body”, “đã biết phí” và “tool/result có hợp lệ không”. Không được trả tiền bằng cách xóa result, hoặc dùng tên container cũ để xóa một instance mới không thuộc mình.

For an authority-database disaster restore:

1. Keep the restored database/workflow/artifact set isolated, with admission and execution disconnected. Record the backup identity/time/frontier, retained evidence sources and missing interval. The disposable Compose database is not a backup system and deliberately loses its data when stopped.
2. Fence the entire pre-restore service: old API writers, schedulers, outbox/workflow workers, model gateways, effect/billing reconcilers and sandbox supervisors. Confirm termination or an enforced boundary for each old environment. Do not infer its death from lease expiry, revoked credentials or a stale snapshot.
3. Invoke the trusted `RuntimeStore.quarantine_restore(new_incarnation, recovery_frontier)` transition using a fresh, non-reused service incarnation and explicit frontier. Restored epochs cannot revive old authority. This revokes prior accepted ownership and retains occupied sandboxes; it is an application transition after controlled data restoration, not the backup restoration procedure itself.
4. Reject delayed old-owner/integrator/verifier/publisher results and old-incarnation commands. Preserve their raw receipts as reconciliation evidence only; they cannot advance current authority. Old stream cursors require an authorized fresh snapshot/reset.
5. Reconstruct beyond-backup effects and charges from retained dispatch/provider/supervisor records. Keep all unknown effects, unknown billing and conservative reserved exposure. Settle each receipt once without inventing a refund or forgetting a possible bill. If missing history prevents bounding exposure or avoiding duplicate effects, keep the affected scope stopped.
6. Verify immutable accepted object bytes and namespace bindings, domain/workflow relationships and retirement evidence. `resume_after_reconciliation(evidence_ref)` requires structured actor-fencing/effect/frontier evidence, retired pre-restore environments and no unresolved effect/billing liabilities. A bare `reconciled: true` cannot authorize it. Evidence dictionaries are references to trusted operator observations; their structure alone does not prove those observations occurred.
7. Acquire fresh ownership and perform a scoped acceptance/cursor check before resuming admission. Retain the incident timeline, prior failures and changed configuration. Do not delete durable events as a rollback mechanism.

**VI:** Nếu backup chỉ biết epoch 2 nhưng worker epoch 5 còn sống, tăng epoch của backup lên 3 không giải quyết quyền của worker cũ. Incarnation mới kết hợp fencing ngoài database cắt thế giới cũ; đối soát sau backup mới giải quyết phần effect và tiền mà snapshot đã mất.

Tested application mechanisms are visible in the store/API/workflow tests: old-owner rejection, cancellation with unknown liabilities, duplicate late settlement, quarantine/reconciliation preconditions, old integration/verifier/publisher rejection and `410` event reset. Opt-in PostgreSQL tests exercise real row locks, database-clock cutoff and these application transitions. The Temporal test executes/replays a bounded local history across ContinueAsNew. These are source and local integration results; consult the final validation report for the exact backend/version and observed pass counts.

**Actual backup export/import, combined PostgreSQL/Temporal/artifact disaster restoration, verified beyond-snapshot reconciliation against real providers, RPO/RTO timing and operated canary recovery remain pending.** No tested `quarantine_restore` call by itself demonstrates those operations. Freeze the failure model, retention, backup cadence, supported compatibility versions and tolerated lost state before a real restore drill; keep candidate environments away from backup/operator credentials.

Schema compatibility is a separate prerequisite. Fresh stores use schema 2; schema 1 is rejected until the [explicit offline identity/writer-protocol migration](../../service/migrations/002_identity-and-writer-protocol.md) runs with quiesced writers, a verified backup and validated disposable copy. It preserves surviving records and liabilities but cannot reconstruct an alias already lost under schema 1. Writer guards are trusted-SQL compatibility checks, not hostile-user isolation. There is no automatic upgrade, in-place downgrade or mixed-version rolling path; a restored old backup must be migrated deliberately before current writers resume.

## Context-aware checkpoint continuation

The opt-in [offloading contract](../../research/context-offloading-spec-2026-10-10.md) uses schema-2 authority storage with versioned `harness_context_v1` checkpoint payloads; this payload version is separate from the database schema version. Keep its accepted projection, raw source/history prefix, exact request, config/adapter identity and allowlist together. Unknown or partially populated typed metadata fails closed. Historical untagged/minimal checkpoints and explicit schema-1 payloads retain their existing legacy recovery behavior. A legacy checkpoint cannot silently enter the new context path, and a typed checkpoint cannot silently fall back to legacy recovery.

Acceptance and model intent commit together. A crash before commit leaves only possible orphan artifacts. A crash after commit retains in-flight exposure, even if the operator suspects no network send occurred. Existing effect reconciliation and physical-retirement gates remain required. Recovery validates the last accepted canonical request without resending it; a new turn needs current ownership and a fresh source frontier. Changes to adapter/configuration require refusal in this slice. Newly written checkpoint records include tenant/task scope; older records are not rewritten. [Current independent review](../../research/context-offloading-independent-review-2026-10-10.md) and [verification](../../research/context-offloading-verification-2026-10-10.json).

**VI:** `schema: 2` trong checkpoint payload không có nghĩa database vừa migrate. Đây là envelope mới trên schema authority hiện tại. Giữ phân biệt này để không dùng compatibility của database làm bằng chứng rằng binary cũ hiểu được recovery semantics mới.
