# Independent Nebius adapter review

Reviewed 2026-10-10 against [NB01–NB10](../../hackathon/00-nebius-protocol-contract.md), the [provider research](provider-and-research.md), and the [implementation record](nebius-implementation.md). This review inspected source and ran synthetic HTTP experiments. It did not query an authenticated catalog, load credentials, purchase inference, or establish live NVIDIA-model capability. The reviewer changed this report only; implementation repairs were performed separately.

## Finding discovered and repaired

**Nullable native fields were incorrectly rejected.** The initial implementation rejected a valid terminal assistant message containing `tool_calls: null`, as well as valid aggregate usage accompanied by null detail objects or null cached/reasoning counters. Independent reproductions returned `ProtocolError: tool_calls must be a list` and `ProtocolError: invalid usage details`. The first case prevented completion; the second kept billing uncertain despite usable aggregate counts.

The public [Nebius OpenAPI schema](https://api.tokenfactory.nebius.com/openapi.json), fetched through an unauthenticated GET during this review, reported version `20260930-cfb76be12`. Its `ChatCompletionResponseMessage.tool_calls` permits array or null; `Usage.prompt_tokens_details` and `completion_tokens_details` permit their respective objects or null; `PromptTokensDetails.cached_tokens` and `CompletionTokensDetails.reasoning_tokens` permit integer or null. No inference endpoint was called.

The repaired [tool normalization](../../service/protocol.py#L210) treats omitted/null tool calls as no calls without modifying the saved native message. [Usage normalization](../../service/providers.py#L179) treats missing/null breakdowns as unavailable detail, pricing prompt tokens at the approved ordinary input rate. Non-null malformed counts remain rejected. [Finish validation](../../service/providers.py#L238) still rejects `finish_reason: tool_calls` without actual tools. The new end-to-end tests preserve null native fields through continuation, retain original response bytes, settle the normalized charge, and replay without HTTP.

**VI:** Schema thật cho phép `null`, nên không thể coi mọi `null` là response hỏng. Sửa này chỉ cho phép trường optional không có dữ liệu; không nới điều kiện chạy tool. Nếu provider báo kết thúc vì tool nhưng không có tool hoàn chỉnh, harness vẫn chặn effect.

**A cache-rate assumption was made enforceable.** Missing/null cache detail is priced at the ordinary input rate. If an approved cache-read rate were higher than that input rate, settlement could understate a charge despite the conservative reservation. The final [Nebius-specific admission guard](../../service/harness.py#L121) rejects such envelopes before dispatch. The [regression](../../tests/test_nebius_provider.py#L504) observes zero Nebius HTTP requests/dispatches while preserving the existing Anthropic path. The reviewer independently ran this added test: **1 passed in 0.30 seconds**. The shared ProviderEnvelope and Anthropic semantics were not changed.

## Measured checks

The reviewer independently ran `.venv/bin/python -m pytest -q tests/test_nebius_provider.py tests/test_live_harness.py tests/test_protocol.py tests/test_engine.py`: **82 passed in 3.69 seconds before repair**, then **97 passed in 3.88 seconds after the nullable-field repair**. The latter includes Anthropic and scripted regression coverage; it is not a rerun of every repository/integration test. Ruff over the four changed service files and Nebius test file passed after repair.

Additional disposable in-memory mock experiments exercised HTTP 429 and HTTP 500 independently. Each produced one request, an Unknown effect with unknown liability and no result artifact; a second harness call refused replay without sending HTTP. A two-tool response followed by terminal response reached completion_proposed and carried correctly ordered native results. These ad hoc checks complement the saved test suite; they are not live-provider evidence.

**VI:** Test đo được hai điều tách biệt: lỗi protocol không tạo effect, và retry/replay không tự gửi request tính phí lần nữa. Các test không chứng minh account có model, giá thật, token cap thật, hoặc model sửa được repository chưa thấy.

## Remaining boundaries

- Successful complete entity bodies are retained, but [HTTP status checking](../../service/providers.py#L316) occurs before reading error bodies. Provider request IDs, rate-limit headers and Retry-After headers are not persisted. The research proposal for that metadata remains unimplemented. Error requests retain conservative liability, so no zero-cost assumption is made.
- The trusted [approval map](../../service/harness.py#L116) is keyed by model and compares the existing rate envelope. Provider/endpoint identity is bound to dispatch evidence and checked during restore; it is not a separate field in the pre-dispatch rate envelope. A future generalized live runner should freeze provider configuration explicitly rather than assume dispatch evidence is the entire approval configuration.
- Output is capped through `max_tokens`, but model-specific reasoning-inclusive enforcement, authoritative input-token bounds, exact response model identity and account rates remain live-preflight requirements. Byte limits are not token counts.
- Only the global endpoint is implemented. Regional APIs, streaming, arbitrary tool schemas, input multimodality, model aliases and automatically retrying injected clients are outside this supported slice. Opaque native assistant fields are retained, but retention alone does not establish provider acceptance of every future field.

The reviewed offline slice demonstrates the intended native protocol and accounting mechanisms after the nullable-field and cache-rate admission repairs. No unresolved blocking defect was found within this bounded mock-tested slice. It does not establish production readiness, an unseen-repository repair result, or Huy's learning/mastery evidence.
